BUILD SPECIFICATION
===================

Project:
Ads/Merchant-style task and order management platform.

IMPORTANT:
The backend must be the single source of truth for:
- order calculation
- task assignment
- working balance
- frozen balance
- profit
- commissions
- deductions
- deposits
- withdrawals
- task limits
- order status

Do NOT perform financial calculations only in JavaScript/frontend.

==================================================
1. ROLES
==================================================

Create four roles:

SUPER_ADMIN
ADMIN/STAFF
MERCHANT
USER

SUPER_ADMIN:
- Full system access
- User management
- Merchant management
- Order management
- Task assignment
- Balance adjustments
- VIP configuration
- Task-limit configuration
- Financial reports
- Audit logs

ADMIN/STAFF:
- Permissions determined by RBAC

MERCHANT:
- Own products
- Own orders
- Order status
- Merchant reports

USER:
- Own tasks
- Own orders
- Own wallet/balance
- Own transaction history
- Own profits

Every API endpoint MUST enforce authorization on the backend.

==================================================

6. ORDER CALCULATION ENGINE
==================================================

Create ONE backend service:

calculateOrder()

Every part of the platform must call this service.

Admin
Merchant
User
Reports
Wallet
Order details

must all use the SAME calculation result.

Never duplicate formulas across different frontend pages.

==================================================
7. CALCULATION FORMULA
==================================================

Base calculation:

subtotal =
unit_price × quantity

Then:

discount_amount =
subtotal × discount_rate

net_amount =
subtotal - discount_amount

tax_amount =
net_amount × tax_rate

processing_fee =
configured fee

gross_amount =
net_amount + tax_amount + processing_fee

Then calculate commission/reward according to the configured business rules.

Example:

unit price = $100
quantity = 2

subtotal = $200

If commission = 10%:

commission = $20

If user reward = 5%:

reward = $10

IMPORTANT:

These percentages are EXAMPLES ONLY.

Store actual rates in configuration/database.

Never hard-code them.

==================================================
8. ROUNDING
==================================================

Use decimal arithmetic.

DO NOT use JavaScript floating-point arithmetic for money.

Store monetary values as:

DECIMAL(18,2)

or use integer cents.

Example:

$125.50

must not become:

125.499999

All calculations must use one consistent rounding policy.

==================================================
9. ORDER SNAPSHOT
==================================================

When an order is created, save the exact calculation parameters used.

For example:

unit_price_snapshot
commission_rate_snapshot
reward_rate_snapshot
tax_rate_snapshot
fee_snapshot

This is critical.

If Admin changes the commission rate tomorrow,
old orders must NOT change.

Old order = historical snapshot.

New order = new configuration.

==================================================
10. WORKING BALANCE
==================================================

The user account has:

working_balance
frozen_balance

Working balance represents the amount available for the platform's defined task/order operation.

Frozen balance represents funds temporarily reserved.

Never directly overwrite balance without a ledger entry.

==================================================
12. BALANCE TRANSACTION
==================================================

Example:

Before order:

working balance = $500

Order requires $100.

If the platform's documented rule is that $100 is reserved:

working balance:
$500 → $400

Create ledger:

ORDER_RESERVE
amount = -100
balance_before = 500
balance_after = 400

When the order completes, perform the configured settlement.

DO NOT simply overwrite:

working_balance = working_balance - 100

without a transaction/ledger record.

==================================================
13. INSUFFICIENT BALANCE
==================================================

If:

required_amount > available_balance

DO NOT secretly force a negative balance.

Instead return:

INSUFFICIENT_BALANCE

with:

available_balance
required_amount
shortfall

Example:

Available:
$300

Required:
$500

Shortfall:
$200

Admin/user interface should clearly display:

Available balance: $300
Required amount: $500
Shortfall: $200

If your legitimate business model permits negative balances, this must be an explicit, documented account state with proper user disclosure and audit logging—not a hidden deduction.

14. TASK CREATION
==================================================

3. Validate target user
4. Validate product
5. Validate merchant
6. Calculate order
7. Check task limit
8. Check balance rules

16. DAILY TASK LIMIT
==================================================

18. PRODUCT PRICE
==================================================

A. Product's configured price

OR

B. Admin override

OR

C. System-calculated amount

Never allow the frontend to silently alter the price.

Store:

product_price_snapshot

on the order.

Example:

must be rejected unless an authorized reversal workflow exists.

30. ATOMIC DATABASE TRANSACTIONS
==================================================

Order creation + task assignment + financial reservation must be atomic.

Pseudo-code:

BEGIN TRANSACTION

validate user
validate product
calculate order
validate limits
validate balance

create order
create task

create ledger transaction

create audit log

COMMIT

If anything fails:

ROLLBACK

==================================================
31. CONCURRENCY
==================================================

Prevent two tasks from spending the same balance simultaneously.

Use:

database transactions
row locking / appropriate isolation
atomic balance updates

Example:

User balance = $100

Two orders arrive simultaneously:

Order A = $80
Order B = $80

The system MUST NOT allow both.

Only one may reserve the available $100 unless the configured business rules explicitly permit otherwise.
